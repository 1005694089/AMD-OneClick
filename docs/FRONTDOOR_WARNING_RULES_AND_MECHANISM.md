# Front-Door Provider Warning Rules and Mechanism

## 1. Purpose

This document defines the responsibilities of the **front-door provider** serving:

```text
https://radeon-global.anruicloud.com
```

The main consumers are server-to-server clients calling `/api/huggingface/*`. The front-door provider protects the public endpoint, warns clients about edge-enforced limits and service conditions, and forwards valid traffic safely to the Radeon origin.

This is a provider-facing contract. It deliberately separates front-door responsibilities from business rules owned by the Radeon application.

## 2. Provider Role

The front-door provider is the public gateway between API clients and the Radeon origin service.

The provider owns:

1. Public DNS and TLS termination.
2. Web application firewall and network abuse protection.
3. Trusted client-IP and forwarding-header handling.
4. Route, method, request-size, and request-time controls.
5. Coarse IP, path, and optionally API-key rate limits.
6. Edge-generated warnings and rejection responses.
7. Origin health checks, failover behavior, and circuit breaking.
8. Request correlation, access logs, metrics, and operational alerts.
9. Safe forwarding of origin responses, including origin warning and rate-limit headers.
10. Protection against direct-origin bypass where the deployment allows it.

The provider does **not** decide:

- Whether a Radeon user has enough credits.
- Whether a caller may use `unlimited_credits`.
- Whether a user already has an active notebook.
- Whether 1, 2, or 4 GPUs can be admitted.
- Which image or notebook source is valid.
- Whether Kubernetes or Hugging Face can complete the requested work.
- Whether a caller owns a specific user or instance.
- Whether a launch retry represents the same logical operation.

Those are origin application responsibilities. The provider transports and preserves their decisions.

## 3. Responsibility Matrix

| Capability | Front-door provider | Radeon origin |
|---|---|---|
| DNS, certificate, TLS policy | Owns | Supplies hostname requirements |
| WAF and bot protection | Owns | Supplies known API patterns |
| Client IP determination | Owns | Trusts only provider forwarding chain |
| Coarse volumetric limits | Owns | Advises expected traffic |
| Per-customer application quota | Optional enforcement from supplied policy | Owns policy and identity source |
| GPU/credit/concurrency admission | Must not infer | Owns |
| Request ID | Creates or validates | Preserves and logs |
| Edge warning headers | Owns | May add origin warnings |
| Origin warning headers | Preserves | Owns content |
| `429` generated at edge | Owns response and retry delay | Not involved |
| `429` generated by origin | Passes through unchanged | Owns response and retry delay |
| Origin health and failover | Owns | Exposes health endpoints |
| Hugging Face upstream handling | Observes only as an origin response | Owns |
| API idempotency | Does not implement business idempotency | Owns |
| Access logs and edge alerts | Owns | Consumes shared telemetry |
| Application audit logs | Does not own | Owns |

## 4. Protected Traffic Classes

| Class | Route | Front-door treatment |
|---|---|---|
| Health | `GET /health` | Health probes plus strict public abuse cap |
| Image catalog | `GET /api/huggingface/images` | Authentication pass-through, short safe caching only if approved, read limit |
| Notebook status | `GET /api/huggingface/notebooks/current` | Polling limit and warning headers |
| Notebook launch | `POST /api/huggingface/notebooks` | Strict body, method, burst, timeout, and abuse controls |
| Notebook delete | `DELETE /api/huggingface/notebooks/current` | Mutation limit and duplicate-request protection at transport level only |
| Disabled GPU endpoint | `GET /api/huggingface/gpus` | Preserve origin `204`; never treat it as a capacity signal |
| Browser/admin traffic | Other routes | Separate policy; do not apply API-client thresholds blindly |

The provider must apply policies by normalized route, not by raw URL alone. Query-string variations must not bypass the selected route policy.

## 5. Request Processing Mechanism

The front door processes each request in this order:

1. Accept TLS using the configured hostname and security policy.
2. Assign or validate `X-Request-Id`.
3. Determine the client IP from the provider-controlled connection context.
4. Remove untrusted forwarding and internal identity headers.
5. Normalize host, path, method, and query information.
6. Apply WAF and threat-intelligence rules.
7. Apply route allowlist, method, header-size, body-size, and timeout rules.
8. Apply IP/path rate and burst controls.
9. If configured, extract a non-secret API-key identifier for a provider-managed quota. Never log the credential value.
10. Select a healthy origin.
11. Forward the request with a new trusted forwarding chain.
12. Preserve safe origin response headers and status codes.
13. Add provider warning, quota, request-correlation, and security headers.
14. Emit structured access telemetry.

A request rejected before step 10 receives a provider-generated response. A request reaching the origin normally receives the origin status and body without semantic rewriting.

## 6. Provider Enforcement Rules

### 6.1 TLS and hostname

The provider must:

- Serve only configured Radeon hostnames.
- Redirect public HTTP to HTTPS, except dedicated internal health paths if required.
- Use TLS 1.2 or later.
- Automate certificate renewal and alert before expiration.
- Reject invalid host headers and domain-fronting attempts.
- Add HSTS only after confirming all public subdomains are HTTPS-compatible.

### 6.2 Trusted forwarding headers

The provider must remove client-supplied values for:

```text
X-Forwarded-For
X-Forwarded-Host
X-Forwarded-Proto
X-Forwarded-Port
X-Real-IP
X-Request-Id
X-Authenticated-Key-Id
X-RateLimit-Scope
X-Internal-*
```

It then creates a trusted forwarding set. If an incoming `X-Request-Id` matches the approved format and policy permits client correlation, the provider may preserve it in a separate header and still create its own provider request ID.

Recommended forwarding contract:

```http
X-Forwarded-For: <verified-client-ip>, <trusted-proxy-chain>
X-Forwarded-Host: radeon-global.anruicloud.com
X-Forwarded-Proto: https
X-Forwarded-Port: 443
X-Request-Id: <provider-generated-id>
X-Frontdoor-Request-Id: <provider-generated-id>
```

The origin must accept forwarding data only from known provider addresses or an authenticated private origin connection.

### 6.3 Route and method rules

| Route | Allowed methods |
|---|---|
| `/health` | `GET`, `HEAD` if required by probes |
| `/api/huggingface/images` | `GET` |
| `/api/huggingface/notebooks/current` | `GET`, `DELETE` |
| `/api/huggingface/notebooks` | `POST` |
| `/api/huggingface/gpus` | `GET` |

For known API routes, unsupported methods return `405 Method Not Allowed` with an `Allow` header. Unknown API routes pass to the origin or return `404` according to the agreed routing model; they must not be redirected to HTML pages.

### 6.4 Request-size and timeout rules

Use a dedicated `/api/huggingface/` policy rather than the long-lived notebook proxy policy.

| Control | Initial value | Provider response |
|---|---:|---|
| Request headers | 16 KiB | `431 Request Header Fields Too Large` |
| Launch JSON body | 32 KiB | `413 Content Too Large` |
| Other API request body | 8 KiB | `413` |
| Header completion | 10 seconds | `408` or connection close |
| JSON body completion | 15 seconds | `408` |
| Origin connect timeout | 5 seconds | `503` |
| Origin first-byte timeout | 30 seconds for management API | `504` |
| Total edge request timeout | 60 seconds for management API | `504` |

Notebook proxy, streaming, image transfer, and WebSocket routes may require separate longer values. Their timeouts must not be inherited by the management API.

### 6.5 WAF and abuse rules

The provider must enable:

- Managed protocol and common exploit rules.
- Request smuggling and conflicting `Content-Length`/`Transfer-Encoding` protection.
- Invalid method, path encoding, and header-character rejection.
- Bot and credential-stuffing controls where available.
- IP reputation rules with an operator allowlist for known partners.
- Detection of repeated authentication failures without inspecting or logging bearer-token values.
- Emergency blocks by IP, ASN, country, path, or API-key identifier.

WAF rules should begin in detection mode, then move to prevention after false-positive review. Provider blocks must use stable reason codes.

### 6.6 Edge rate limits

These are coarse protection defaults, not GPU or credit policy.

| Scope | Route class | Initial limit | Burst |
|---|---|---:|---:|
| Client IP | Entire origin | 300/minute | 100 |
| Client IP | Failed authentication responses | 20/minute, 100/hour | 10 |
| Client IP | Launch path | 20/minute | 5 |
| Client IP | Status path | 180/minute | 30 |
| Client IP | Health path | 60/minute | 20 |
| API key ID, if available | Launch path | 10/minute | 3 |
| API key ID, if available | Status path | 120/minute | 30 |

Rules:

- IP limits protect infrastructure but must not be treated as customer quotas.
- The provider should prefer verified API-key identity over IP when the identity can be derived safely.
- Shared NAT addresses and cloud egress can represent many legitimate users; allow per-partner overrides.
- Do not count provider health probes against public limits.
- Do not count one rejected request against multiple provider limit buckets unless documented.
- The origin remains authoritative for weighted GPU limits, active-instance limits, user ownership, and credits.

### 6.7 Origin protection

The provider must:

- Prefer private connectivity, origin allowlisting, mutual TLS, or a rotating origin secret.
- Prevent public clients from reaching the origin directly when possible.
- Set the origin `Host` header to the agreed value.
- Limit connections and request concurrency sent to the origin.
- Queue only small, bounded bursts. Do not build an unbounded queue in front of launch requests.
- Stop sending traffic to an unhealthy origin according to health policy.
- Never replay `POST` or `DELETE` automatically unless the origin and provider explicitly support safe replay.

## 7. Warning Rules Owned by the Provider

The provider reports only conditions it can measure or enforce.

| Warning code | Trigger | Severity | Behavior |
|---|---|---|---|
| `edge_rate_limit_near` | 70–89% of provider limit | Advisory | Allow and add warning headers |
| `edge_rate_limit_critical` | 90–99% | Critical | Allow eligible request and add warning headers |
| `edge_rate_limit_exceeded` | Provider limit exhausted | Blocked | Return `429` |
| `origin_degraded` | Elevated origin errors/latency below failover threshold | Advisory or critical | Allow safe traffic; warn |
| `origin_unavailable` | No healthy origin | Blocked | Return `503` |
| `origin_timeout` | Origin deadline exceeded | Blocked | Return `504` |
| `maintenance_soon` | Scheduled maintenance window published | Advisory | Add warning and maintenance time |
| `credential_migration` | Provider was given a legacy-key classification | Advisory | Preserve supplied deprecation metadata |
| `certificate_risk` | Provider certificate approaches expiry | Operator-only critical alert | Do not expose unnecessary detail publicly |
| `waf_suspicious` | Request matches detection rule but policy allows it | Operator-only or client advisory | Never reveal exploitable rule internals |

The provider must not emit warnings such as `insufficient_credits`, `gpu_capacity_low`, or `active_instance_exists` unless the origin explicitly returned those conditions.

## 8. Provider Response Contract

### 8.1 Headers on successful API responses

```http
X-Request-Id: 01J...
X-Frontdoor-Request-Id: 01J...
RateLimit-Policy: "edge-status";q=180;w=60
RateLimit: "edge-status";r=84;t=37
X-Warning-Level: advisory
Warning: 299 - "Approaching the front-door request limit"
```

Rules:

- Include rate-limit headers only for the policy applicable to the response.
- Identify edge policies with names beginning `edge-`.
- Do not overwrite origin application policies such as `app-launch-units`.
- If both provider and origin limits apply, preserve the origin fields and expose the provider policy in separately named headers or a combined standards-compliant policy list agreed with the origin team.
- Never put bearer tokens, raw API keys, private URLs, node names, or internal addresses in response headers.

### 8.2 Provider-generated `429`

```http
HTTP/1.1 429 Too Many Requests
Content-Type: application/problem+json
Retry-After: 37
RateLimit-Policy: "edge-launch";q=20;w=60
RateLimit: "edge-launch";r=0;t=37
X-Request-Id: 01J...
Cache-Control: no-store
```

```json
{
  "type": "https://radeon-global.anruicloud.com/problems/frontdoor-rate-limit",
  "title": "Front-door rate limit exceeded",
  "status": 429,
  "detail": "The request exceeded the provider's launch-path rate limit.",
  "code": "edge_rate_limit_exceeded",
  "request_id": "01J...",
  "source": "frontdoor",
  "retry_after_seconds": 37
}
```

### 8.3 Provider-generated dependency errors

| Condition | Status | Required headers/code |
|---|---:|---|
| No healthy origin | `503` | `Retry-After`, `origin_unavailable` |
| Origin connection failure | `503` | `Retry-After`, `origin_connect_failed` |
| Origin response timeout | `504` | `origin_timeout` |
| Provider overload | `503` | `Retry-After`, `frontdoor_overloaded` |
| Scheduled maintenance block | `503` | `Retry-After`, `maintenance` |

Use `application/problem+json` for provider-generated API errors. Never replace an origin-generated `400`, `401`, `402`, `403`, `409`, `422`, or `429` with a generic provider error.

### 8.4 Origin response preservation

The provider must preserve:

- Origin status code and response body.
- `WWW-Authenticate` on `401`.
- `Allow` on `405`.
- `Retry-After` on `429` and `503`.
- `RateLimit` and `RateLimit-Policy`.
- `Deprecation`, `Sunset`, and approved warning headers.
- `Content-Type`, caching directives, and safe correlation headers.

The provider may remove hop-by-hop headers, unsafe internal headers, and headers explicitly listed in the provider-origin contract.

## 9. Origin Health and Circuit-Breaker Role

### 9.1 Health checks

The provider should probe a lightweight readiness endpoint that confirms the manager can accept API traffic. `/health` currently returns a basic process-level result; the Radeon team should expose separate liveness and readiness endpoints if dependency-aware routing is required.

Provider health probes must:

- Use a dedicated user agent and, if needed, a private authentication method.
- Bypass public customer rate limits.
- Use a short timeout.
- Avoid creating sessions, users, notebooks, or billable work.
- Be logged separately from customer traffic.

### 9.2 Passive health

The provider may consider connection failures, timeouts, and selected `5xx` responses when evaluating origin health. It must not mark the origin unhealthy because of normal client errors such as `400`, `401`, `403`, `409`, `422`, or application `429`.

### 9.3 Circuit breaking

Initial policy:

- Open the circuit after at least 10 transport failures and a failure ratio above 50% in 30 seconds.
- Keep the circuit open for 30 seconds.
- Allow limited half-open probes.
- Close after 3 consecutive successful probes.
- Return `503` with a bounded `Retry-After` while open.

Tune values from production data and origin replica count.

## 10. Logging, Metrics, and Alerts

### 10.1 Provider access log

Log:

- Timestamp, provider request ID, and upstream request ID if supplied.
- Verified client IP or privacy-preserving representation.
- Host, normalized route, method, status, bytes, and latency.
- Selected origin, connect time, first-byte time, and total origin time.
- WAF action and stable rule category.
- Applied rate policy, remaining amount, and reset time.
- Provider warning code and decision: `allow`, `warn`, `throttle`, or `block`.
- API-key identifier only when safely derived; never log the credential.

Do not log:

- `Authorization` values.
- `HF_TOKEN`, `git_token`, cookies, or session secrets.
- Full request bodies by default.
- Private repository credentials or signed URLs.

### 10.2 Provider metrics

At minimum:

- Requests, bandwidth, status, and latency by normalized route.
- WAF detection/block counts by category.
- Edge `429`, `503`, and `504` counts.
- Origin connection errors, timeouts, and health state.
- Rate-limit utilization and warning count.
- Active connections, queued requests, and rejected overload traffic.
- TLS handshake failures and certificate expiry time.
- Direct-origin bypass attempts if visible.

Avoid raw IP, API key, user name, or request ID as metric labels.

### 10.3 Initial provider alerts

- Critical: no healthy origin for 1 minute.
- Critical: edge-generated `5xx` exceeds 5% for 5 minutes.
- Critical: origin bypass protection is disabled unexpectedly.
- Critical: certificate expires within 7 days.
- High: origin timeout rate exceeds 2% for 5 minutes.
- High: WAF blocks or authentication failures rise to 5x baseline.
- High: edge `429` exceeds 20% for a partner or route for 15 minutes.
- Warning: provider limit utilization exceeds 80% for 15 minutes.
- Warning: certificate expires within 30 days.

## 11. Handoff Contract with Radeon Origin

The Radeon team must provide the front-door provider with:

1. Public hostname and certificate ownership model.
2. Origin addresses, ports, protocol, and expected `Host` header.
3. Private connectivity or origin-authentication configuration.
4. Route and method inventory.
5. Which routes support WebSocket, streaming, or long-running responses.
6. Expected normal and peak request rates by route.
7. Safe request-body limits and timeout requirements.
8. Health endpoint and success criteria.
9. Headers that must be preserved or removed.
10. Planned maintenance windows and client-facing text.
11. Emergency contacts and escalation severity definitions.
12. Partner IP or API-key-ID exceptions.

The provider must return:

1. Provider IP ranges or private-link information.
2. Forwarding-header contract.
3. WAF and rate-limit policy identifiers.
4. Provider-generated error schema.
5. Logging fields and retention policy.
6. Dashboards, alerts, and escalation contacts.
7. Change-management and rollback procedure.
8. Evidence from bypass, overload, timeout, and failover tests.

## 12. Origin-Owned Rules the Provider Must Preserve

The following decisions remain with FastAPI and must pass through the front door:

- Bearer-token validity and application scopes.
- User ownership and normalized `user_name` rules.
- Credit balance and `unlimited_credits` authorization.
- One-active-instance policy.
- GPU count, weighted launch budget, active GPU cap, and capacity admission.
- Image, notebook URL, Git repository, and `git_token` validation.
- Idempotency for launch and delete.
- Kubernetes and Hugging Face upstream classification.
- Application `400`, `401`, `402`, `403`, `409`, `422`, `429`, `502`, `503`, and `504` responses.
- Application warnings such as credential expiry, launch budget, insufficient credits, or GPU availability.

The provider may add an edge warning but must not alter the meaning of an origin decision.

## 13. Rollout Plan for the Provider

### Phase 0 — Baseline

- Inventory routes and origin paths.
- Enable provider request IDs and access logs.
- Run WAF and rate policies in detection/shadow mode.
- Measure normal traffic, shared IPs, request sizes, and origin latency for at least one representative week.

### Phase 1 — Safe protocol enforcement

- Enforce TLS, host, forwarding-header, malformed-request, method, and body-size rules.
- Add the dedicated management API timeout policy.
- Confirm browser/notebook routes are unaffected.

### Phase 2 — Warnings

- Return provider `RateLimit`, warning, and request-correlation headers.
- Publish provider problem codes and retry guidance.
- Deliver dashboards to the Radeon team.

### Phase 3 — Rate and origin protection

- Enforce failed-auth, path, and coarse IP limits.
- Add API-key-ID limits where a safe identity integration exists.
- Enable origin connection/concurrency limits and circuit breaking.
- Verify origin responses and warnings pass through unchanged.

### Phase 4 — Bypass and failure testing

- Test direct-origin access denial.
- Test provider overload, origin down, origin slow, and all-origins-unhealthy behavior.
- Test shared NAT clients and partner exceptions.
- Test rollback for every blocking policy.

### Phase 5 — Production tuning

- Review false positives and limit utilization monthly.
- Require change approval for blocking rules.
- Re-run failover and emergency-block exercises quarterly.

## 14. Provider Acceptance Criteria

The front-door provider is ready when:

- Only approved hostnames and TLS versions are accepted.
- Client forwarding and internal identity headers cannot be spoofed.
- Management API routes have dedicated size and timeout policies.
- Provider rate limits return stable warnings, `429`, and `Retry-After` behavior.
- Origin `401`, `409`, `429`, warning, deprecation, and quota headers survive the proxy.
- Provider errors are distinguishable with `source: frontdoor` and a request ID.
- Health checks create no user or GPU work.
- The provider never automatically replays a launch mutation.
- Direct-origin bypass is blocked or explicitly documented and monitored.
- Logs contain no bearer tokens or credential-bearing request bodies.
- Radeon and provider operators can correlate one request across both layers.
- Overload, origin failure, timeout, failover, and rollback tests pass.
